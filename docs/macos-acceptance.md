当前登记为“Mac 单 Worker 基线工程交付，业务验收待完成”。本轮只验收分支分析与覆盖率分析，不以风险发现数量为目标。构建成功、下载后的本机首次启动、模型完成、业务结论正确和实测覆盖率提升分别记录。

## 启动与输入

双击随包的 `PANGEA Desktop Acceptance.app`。验收通道使用独立 appId、默认 profile 和该 profile 下的 `launch-root`；不要改成正式 profile，也不要复制已有 Run、报告、技能或凭据。保留整个验收包供重启续查。界面要求配置真实分析执行器时，在这个隔离实例内完成配置和连通性检查。

本包使用 ad-hoc 验收签名，未做 Developer ID 公证。GitHub runner 的启动通过不证明下载件能通过本机 Gatekeeper。先在 Finder 正常打开应用；系统提示未验证开发者时，核对下载来源后，通过系统“隐私与安全性 → 仍要打开”授权这一应用。脚本不代替这一步，也不关闭 Gatekeeper、删除 quarantine 或重新签名。

`2.1.4-macaccept.2` 的用户本机复验记录为：哈希及启动前签名通过，带 quarantine，`spctl` 拒绝，烟测在独立执行内置 Node 时超时，尚未进入工作台。两者因果未确认；这既不证明包已损坏，也不能登记为本机启动通过。完成首次授权后的 Finder 启动仍须在受影响 Mac 复验。

若仍未进入工作台，随包 `diagnose-macos-startup.sh` 不依赖系统 Python 或内置 Node 来启动诊断。它先采集系统版本、签名、quarantine 和系统评估，再用有时限的独立 Node 探针保留 stdout/stderr、PID、退出码和超时现场；不会启动分析、读取模型凭据或改用户 profile。在验收包所在目录执行一次 `sh diagnose-macos-startup.sh "PANGEA Desktop Acceptance.app"`，即可生成独立 `pangea-macos-startup.*` 证据目录。脚本结束仅表示收集结束，各项结果以 `checks.tsv` 为准；不据 `spctl` 非零或单次超时自动归因。

第一次启动先确认能进入工作台、设置页能识别实际执行器与模型、源码目录可选择。没有模型或认证失败应显示具体原因；不可把“进程存在”作为模型联调成功。

## 两个独立 Run

先通过源码仓库入口导入或选择 `keyring-source`，核对预览恰好包含四个 `.c`、两个 `.h`；LICENSE 不承担分析职责。只选择下列六份源码，避免把夹具说明、覆盖率 JSON 或验收文档作为源码：

```text
module/keyring/file/keyring.c
module/keyring/file/keyring_rpc.c
lib/keyring/keyring.c
lib/keyring/keyring_rpc.c
include/spdk/keyring.h
include/spdk/module/keyring/file.h
```

1. **分支 Run**：新建分析 → 分析目标类型“产品行为” → 场景“分支分析”。目标采用 `branch-task.txt`，选择上述冻结范围，不附加合成覆盖率文件。使用标准复核方式，观察独立盲审与随后对照的真实会话记录。
2. **覆盖率 Run**：重新新建分析 → 场景“覆盖率分析”，使用同一源码范围；在覆盖率输入中选择文件导入，导入 `coverage-synthetic.combined.json` 并选中解析后的资产。本轮不调用内网查询技能。目标写明“依据合成缺口设计补测，验证输入关联与未知保留；不声称实测覆盖提升”。

覆盖率 JSON 应解析为四条定位记录：一条函数缺口、一条行缺口、一条计数为 0 的分支、一条计数未知的分支。未知分支不能作为已确认零覆盖目标；分支 block/branch 是夹具坐标，不能据编号猜 true/false。该数量是导入检查，不是强制生成四条用例。

## 手动验收判据

| 入口 | 应观察的行为 | 不接受的结果 |
| --- | --- | --- |
| 新建分析与输入预览 | 场景、范围、模型及覆盖率资产清楚；冻结范围与选择一致 | 选择小范围后仍整仓分析；缺模型却回显已就绪 |
| 分支结果 | 中间条件保留前序校验；同对象互斥状态与同名不同对象并存区分；时序和恢复约束进入用例或明确缺口 | 按每个 if 拆例；相同错误码即合并；将旧/新对象混同；困难场景被删掉 |
| 覆盖率结果 | 关联到本次冻结源码；区分零覆盖、未知和没有采集；业务用例与 coverage 记录显式关联 | 把未知变 0；把已设计当已执行；把合成计数描述为真实平台采集或覆盖率增长 |
| 业务流程 | 流程图、时序图、函数变量图可查看，节点/路径关联对应实际用例；缺关系如实保留 | 名称相似就关联；旧对象消失等同全局列表为空；图能显示就宣布覆盖完整 |
| 用例与导出 | 标题、前置、步骤、预期、观察点、清理动作完整；缺消费方驱动的场景保留准备度 | 凭源码 API 虚构产品 CLI、注入工具或现成测试设施 |
| 复核与返回 | 能从失败单元定位会话；问题回实际作者；定向修正保留其他正确结果；返回用例列表位置稳定 | 宿主补造业务答案；修一个映射重做全单元；报告完成但仍永久计时 |
| 重启查看 | 已完成 Run、图、用例和报告仍能打开 | 重启产生重复 Run 或覆盖旧结果 |

仅在隔离实例对本次新建任务验证停止/重试，不操作已有生产 Run。记录 Run ID、任务/会话 ID、模型名、版本清单及具体失败步骤；保存诊断日志前移除凭据。不要手工修改 `progress.json` 或调用完成/绑定工具制造成功状态。

## 结论边界与真实业务验收

本次锁定的 Agent 已修复 combined 响应顶层 `product/c_version/b_version` 未进入 acquisition 的问题。三个字段原样保留，缺失、null 和空字符串不以请求值替代。回归覆盖原始资产→解析→冻结诊断→Planning／Analysis／独立盲审／同 Reviewer 对照的实际 `input_read`，并确认重解析资产不改写已有 Run 的冻结输入。构建同时在成品自带 Python 中执行此回归，检查导入路径确属包内运行时。这是数据传递与协议测试，使用人工协议产物，没有调用真实模型，不证明分析质量或拆分有效。

以上小样本用于 Mac 启动、真实模型链路、输入消费、分支语义、图文与导出的基线验收。源码真实，覆盖率计数合成；SPDK 未执行，消费方驱动及故障设施未提供。不存在真实 compaction 事件及前后产物时，压缩保留能力记“未观察”，不能记通过。

真实业务验收还需同一版本源码及必要上下游、可复现的业务任务、实际执行器，以及真实覆盖率导出/平台响应（范围、版本、来源、分页/快照、零计数与未知语义）。验证覆盖率提升时必须补上执行记录和前后同口径采集。FIN/RST 与主动断链交错须使用对应协议源码与操作环境，不能从 keyring 顺序生命周期外推。下一轮 Worker 拆分对照需另行实现和冻结版本；本包只是其单 Worker 基线。
