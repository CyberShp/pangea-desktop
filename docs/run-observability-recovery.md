# 运行进展与恢复

任务概览增加执行进展摘要；“运行过程”展示当前阶段、真实执行活动、最近结果保存时间、
单元提交进度和最近通信。展开“查看保留成果与待处理任务”，可查看每项任务保存的版本、
记录数量、已接受或草稿状态，以及下一步是接收提交还是续接原执行。

## 展示依据

- 阶段来自当前 Run 的 Graph；单元总数来自本次冻结的规划。
- 有效进展取结果文件的实际写入时间。通信或界面轮询不会让该时间前移。
- ACP 活动只取结构化工具事件和协议活动。普通读取工具显示“读取工具执行中”，
  不据工具名称或模型文字推断它正在阅读源码；缺少活动证据时显示未记录。
- 完成提交、已接受结果和审查 PASS 分别呈现。保存草稿或达到执行预算不产生质量结论。
- 刷新失败时显示上次记录，并说明当前执行状态未知；历史运行缺少时间字段时显示未记录。

## 停止与续接

停止会保留冻结输入、已保存结果和已完成提交，并阻止停止后的结果写入。
继续时先接收已经声明完成的保存结果；未完成任务续接原任务及原会话，不重复派发已完成任务。

每个实际执行回合使用独立执行编号，重复开始通知不重复累计回合，旧回合的迟到通知不能
覆盖新回合。宿主确认旧执行已经停止后才恢复失联任务；进程仍存活或无法确认时保持阻塞，
不以宿主内存中没有 Job 为由启动第二个执行，也不自动终止未知进程。

定向修正达到预算后，已完成成果和未解决任务继续保留。用户可以继续原任务，或交付已有结果。
部分交付先持久化报告阶段；报告组装途中中断后只继续组装，不重跑分析或修正。
重复交付请求返回同一已完成交付，不生成第二份语义结果。

## 验证入口

Agent 的 `verification/observability_recovery.py` 使用真实 Graph、冻结输入、结果写入和报告接口，
覆盖停止恢复、重复与迟到执行事件、已提交成果续接及报告写入后的故障恢复。
Windows 打包脚本使用实际待打包 Agent 与嵌入式 Python 执行该验证。

Companion 的运行投影和交互回归检查有效进展、通信时间、恢复阻塞及历史字段缺失。
`tests/recovery-harness.integration.mjs` 用真实 Cordis/Jobs、ACP stdio 测试进程和 Python CLI
验证故障恢复。所需宿主依赖安装在隔离目录，不修改项目依赖。

本轮环境没有 NGA 可执行程序，也没有运行 Windows 成品。协议测试进程能验证宿主恢复和
数据边界，不能替代真实 NGA 的断连、重启与超时验收。
